# 検査用の語の一覧の案（因果語・仮説の語尾・比較語）

**状態: 案（未承認）。** この文書の語は、承認されるまで設定ファイルへ入れない。承認者名と承認日は、タスク13.1に記録する（design.mdの「因果語・仮説語・比較語の承認の流れ」段階1）。

## 読み方

- 検査の実装は`apps/api/src/regional-values/draft/checks.ts`にある。語の一致は、全角半角などをそろえた（NFKC）うえでの部分一致である。
- 因果語（`DR_CAUSAL_CLAIMS`）: 課題候補の文（候補の文、事実の要約、背景）に、一覧の語が1つでもあれば不合格にする。仮説の語尾が付いていても不合格にする。たとえば「〜が原因である可能性があります」は、因果語の検査で不合格になる。
- 仮説の語尾（`DR_HEDGE_REQUIRED`）: 候補の文が、末尾の句点を除いて、一覧のいずれかで終わらなければ不合格にする。事実の要約と背景には課さない。
- 比較語（`DR_COMPARISON`）: 一覧の語を含む文は、2件以上の事実項目を根拠に持ち、単位、対象地域、調査年または基準日がそろっている場合だけ合格にする。語を含まない文には課さない。
- 検査に合格しても、人のレビュー（確認項目のうち因果関係の項目）を経るまで承認しない。語の一覧にない言い回しは、人が確認する。
- **過検出と未検出の扱い**: 過検出（因果でない文を不合格にする）は、下書きの再生成で済む。未検出（因果の断定を通す）は、人のレビューでしか止められない。そのため、迷う語は「要判断」とし、拾う側に倒した案を示している。
- 各表の「検出される例」「検出されない例」は、この案の一覧に対して手元で確かめた架空の文である（実在の統計ではない）。
- 「採否」の欄は承認者が書く（採用、不採用、修正案）。空欄の語は採用しない。

## 既存の一覧との重なり

- リポジトリの設定のうち、`neutrality.json`、`build.json`、`draft.json`は未作成である（`config/regional-values/`には`map.json`だけがある）。否定表現、排他的な語、優劣などの語の一覧（design.mdのOpen Decisions (7)(18)）も未承認のため、重なりの照合は、それらの承認後に行う。
- 試験専用の設定（`tests/harness/regional-values/test-config/neutrality.json`）との重なりは、否定表現の`より`が比較語`より多`などの一部になる点だけである。`より`は対応方向の説明に、比較語は課題候補の文に使うため、適用先が異なる。
- 比較語の`最も`は、優劣の語（`SUPERIORITY`）の承認待ちの一覧と重なる可能性がある。

## 2. 仮説の語尾（`hedgeEndings`）

候補の文は、次のいずれかで終わる必要がある。すべて敬体（です・ます）の形で、設計の例と試験専用の設定に合わせている。常体（「可能性がある」）を認めるかどうかは、承認者が決める。

| 語尾 | 提案 | 理由 | 合格する文の例 | 不合格になる文の例 | 採否 |
| --- | --- | --- | --- | --- | --- |
| `可能性があります` | 採用案 | 仮説の語尾の基本形 | 「移動手段の少なさが、通院の負担になっている可能性があります」 | 「移動手段の少なさが、通院の負担になっています」 |  |
| `可能性も考えられます` | 採用案 | ほかの説明も残す言い方 | 「移動手段の少なさが、通院の負担になっている可能性も考えられます」 | 「移動手段の少なさが、通院の負担になっていると言えます」 |  |
| `可能性が考えられます` | 採用案 | 「可能性があります」の言い換え | 「移動手段の少なさが、通院の負担になっている可能性が考えられます」 | 「移動手段の少なさが、通院の負担になっている可能性が高いです」 |  |
| `可能性があると考えられます` | 要判断 | 和らげを重ねた形。「考えられます」で終わるので、独立した語として必要 | 「移動手段の少なさが、通院の負担になっている可能性があると考えられます」 | 「移動手段の少なさが、通院の負担になっていることが分かります」 |  |
| `かもしれません` | 採用案 | 推量の語尾 | 「移動手段の少なさが、通院の負担になっているのかもしれません」 | 「移動手段の少なさが、通院の負担になっているはずです」 |  |
| `のではないかと考えられます` | 要判断 | 「ではないか」を含み、仮説であることが明確 | 「移動手段の少なさが、通院の負担になっているのではないかと考えられます」 | 「移動手段の少なさが、通院の負担になっていると考えられます」 |  |

提案の件数: 6件（採用案4件、要判断2件）。

提案しない語尾:

| 語尾 | 提案しない理由 |
| --- | --- |
| `と考えられます` | 「可能性」などの限定がなく、結論として読める |
| `と思われます` | 同上 |
| `でしょう` | 推量だが、断定の和らげとして読まれることがある |
| `ようです` | 伝聞の形で、課題の仮説の語尾として使うと出典がない主張に見える |

## 3. 比較の語（`comparisonWords`）

この一覧の語を含む文は、2件以上の事実項目を根拠に持つ必要がある。下の「検出される例」は、根拠が1件の事実項目だけなら不合格になる文である。

| 語 | 提案 | 理由 | 検出される例 | 検出されない例 | 採否 |
| --- | --- | --- | --- | --- | --- |
| `比べ` | 採用案 | 「比べて」「に比べ」「比べると」をまとめて拾う | 「A地域はB地域に比べて、値が大きいです」 | 「A地域の値は、調査年とともに示されています」 |  |
| `比較` | 採用案 | 「比較して」「と比較」を拾う。「比較的」も拾う（2件の根拠を求める側に倒す） | 「前年と比較して、値が変わっています」 | 「前年の値が示されています」 |  |
| `並べ` | 要判断 | 2つの値を並べて見せる形（「並べて示す」） | 「二つの年の値を並べて示します」 | 「ある年の値を示します」 |  |
| `より多` | 採用案 | 「より多い」「より多く」を拾う | 「A地域はB地域より多いです」 | 「A地域の数が示されています」 |  |
| `より少` | 採用案 | 「より少ない」「より少なく」を拾う | 「A地域はB地域より少ないです」 | 「A地域の数が示されています」 |  |
| `より高` | 採用案 | 「より高い」「より高く」を拾う | 「A地域はB地域より高いです」 | 「A地域の割合が示されています」 |  |
| `より低` | 採用案 | 「より低い」「より低く」を拾う | 「A地域はB地域より低いです」 | 「A地域の割合が示されています」 |  |
| `上回` | 採用案 | 「上回る」「上回って」を拾う | 「A地域の値は、B地域を上回っています」 | 「A地域の値が示されています」 |  |
| `下回` | 採用案 | 「下回る」「下回って」を拾う | 「A地域の値は、B地域を下回っています」 | 「A地域の値が示されています」 |  |
| `超え` | 要判断 | 基準値との比較。「県境を超えて」のような比較でない文も拾う | 「利用者数が基準を超えています」 | 「利用者数が示されています」 |  |
| `との差` | 要判断 | 2つの値の差を述べる形 | 「前年との差が見られます」 | 「前年の値が見られます」 |  |
| `格差` | 採用案 | 地域や年の間の差を述べる語 | 「地域間の格差があります」 | 「地域ごとの値が示されています」 |  |
| `倍` | 要判断 | 比を述べる形（「二倍」「倍増」） | 「前年の二倍になっています」 | 「前年の値が示されています」 |  |
| `最も` | 要判断 | 最上級は、複数の対象の比較を前提にする。優劣の語（SUPERIORITY）の承認待ちの一覧と重なる可能性がある | 「A地域が最も値が大きいです」 | 「A地域の値が示されています」 |  |

提案の件数: 14件（採用案9件、要判断5件）。

提案しない語:

| 語 | 提案しない理由 |
| --- | --- |
| 高い、低い、多い、少ない、大きい、小さい | 1件の事実項目だけの文にも使う（過検出が多すぎる） |
| 増加、減少、増え、減っ | 推移を示す1件の事実項目の文にも使う |
| 平均、全国、県内 | 事実項目の名称や対象地域にも現れる |
| 最大、最小、一番 | 「最も」と同じ扱いにするなら、そちらに加える（要判断） |

## 承認者に決めてほしい点

1. 仮説の語尾に常体（「可能性がある」）を認めるか。
2. 仮説の語尾が付いた因果の文（「〜が原因である可能性があります」）を、因果語の検査で不合格にする運用でよいか（Req 8.26の(a)と(b)を重ねた結果であり、案はこの運用に合わせている）。
3. 「要判断」の語の採否。
4. 3つの一覧の置き場所。設計は`neutrality.json`としているが、実装（`draft run`、`issues export`、`build --draft-settings`）は、`--draft-settings`で渡す設定ファイル（`DraftRunSettingsSchema`。実ファイルは13.1の`draft.json`の想定）から3つの一覧を読む。13.1の前に、どちらかへそろえる必要がある。

## 承認後の手順

1. 承認者名と承認日をタスク13.1に記録する。
2. 承認された語だけを設定へ入れ、3つの一覧の正準JSONのSHA-256を`records/word-lists-approval.json`に記録する。
3. `repoConfigFixtures.test.ts`が設定と記録のSHA-256の一致を検査する。
